## Static frontend and request routing

Astro supports static output, a deployment `base`, directory-style build output and selective client interaction. Proposed configuration choices are `output: 'static'`, `base: '/practice'`, `trailingSlash: 'always'` and directory output; no configuration file is created in Chunk 1. Use a central base-aware link helper, static navigation and generated `index.html` files. The actual host determines prerendered trailing-slash redirects, so canonical/redirect checks belong in deployment validation. [Astro configuration reference](https://docs.astro.build/en/reference/configuration-reference/), [rendering guide](https://docs.astro.build/en/guides/on-demand-rendering/).

The standard single-site WordPress rule skips existing files and directories using `!-f` and `!-d`; the actual root `.htaccess` must still be read and hashed. [WordPress reference](https://developer.wordpress.org/advanced-administration/server/web-server/httpd/). These tests concern the **requested resolved path**, not a blanket exemption of every possible descendant merely because `/practice/` exists. Apache also has configurable parent/child rewrite inheritance. [Apache mod_rewrite](https://httpd.apache.org/docs/2.4/mod/mod_rewrite.html).

**Design recommendation:** emit physical directories for every public static URL, keep routing rules local to the Lab directory, and keep the root WordPress rules unchanged. Verify the following on password-protected staging before any production deployment: physical page, asset, API collection, API item, query state, unknown Lab URL, unknown WordPress URL, and all HTTP methods. A proposed Lab front controller and child rules are not verified by the mere presence of `!-d`. If clean API routes cannot bypass WordPress safely without parent changes, a physical API entry point with a validated route query is a viable HTTP API fallback; otherwise use an independently hosted API, rather than silently editing the root rules.

## Storage and deterministic sessions

SQLite WAL permits readers and a writer concurrently, but still only one writer at a time. WAL requires cooperating processes on one machine and is unsuitable for a network filesystem. [SQLite WAL](https://sqlite.org/wal.html), [SQLite isolation](https://sqlite.org/isolation.html). A SQLite database file and its journal/sidecar directory must be kept outside every public document root. PHP supports absolute file DSNs; an in-memory DSN does not provide an ordinary persistent cross-request store. [PDO SQLite DSN](https://www.php.net/manual/en/ref.pdo-sqlite.connection.php).

**Design recommendation if actual SQLite capability is established:** immutable versioned seed data plus session-keyed copy-on-write rows in a private Lab database; cryptographically random session capability independent of deterministic fixture seeds. Validate session identifiers before database use, never turn a client identifier into a filesystem path, scope every query to the session, and use prepared statements. Keep transactions short; apply artificial delays outside transactions and PHP session locks. Use a bounded busy timeout and distinguish genuine capacity failures from simulated exercise errors. A reset clears only the caller's overlay. TTL cleanup and global caps prevent unbounded growth. Validate concurrent writes, expiry/reset races and cross-session isolation before release. If SQLite is unavailable, choose a separately credentialed Lab MariaDB database or isolated external runtime through an explicit ADR; never reuse WordPress storage.

## Same-origin and process isolation

Cookie `Path` narrows when browsers send cookies but is not a security boundary. Origins are distinguished by scheme, host and port, not URL path. [Cookie semantics](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), [same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy). WordPress sets login cookies using configured cookie path/domain constants. [WordPress auth-cookie implementation](https://developer.wordpress.org/reference/functions/wp_set_auth_cookie/).

**Design consequence:** `/practice/` shares a browser origin with WordPress. Root-scoped WordPress cookies may arrive at Lab requests even though the Lab does not use them. A separate database is data isolation, not a separate operating-system or browser trust boundary. PHP running under the same account identity may retain permission to read sibling WordPress files; do not claim otherwise without effective permission evidence.

Required Lab safeguards: do not import/bootstrap WordPress, read its configuration, accept its credentials, inspect or log its cookies, proxy WordPress routes, or issue WordPress writes. Use a distinct secure HttpOnly Lab cookie (host-only, Path limited to Lab, appropriate SameSite) or an explicit `X-Lab-Session` bearer; exclude those secrets from logs. Never support user-supplied executable HTML/JavaScript, arbitrary uploads, SQL, remote URLs or commands. Simulate defects as fixed allowlisted states. Use contextual output encoding, restrictive CSP and no origin-wide service worker. If a future exercise needs execution of untrusted content, move it to an isolated origin and sandbox rather than weaken these safeguards. Strong runtime isolation requires a separate service identity/container/account; a subdomain alone does not establish that or remove parent-domain cookies.

## Atomic releases and cache controls

Linux `rename` replaces an existing destination atomically within the same filesystem; cross-filesystem renames fail, and symlink operands rename the link itself. [Linux rename semantics](https://man7.org/linux/man-pages/man2/rename.2.html). **Proposed method:** fully upload and verify an immutable release, create a temporary link beside the live Lab link, then atomically rename the temporary link over the existing link with no directory dereferencing. A remove-then-link sequence and a two-directory rename sequence do not provide the same atomic guarantee.

Preconditions to record before promising this method: shell access; actual symlink support; approved Lab-only target paths; same-filesystem link switch; server permission to traverse the link; reliable PHP realpath/opcache behavior; a lock against simultaneous deploys; versioned asset availability for in-flight pages; and database schema compatibility with the three retained releases. A production directory already containing files cannot simply be overwritten with a symlink. Initial installation needs its own scoped cutover. Proposed later wrapper: `node practice-lab/scripts/deploy.mjs rollback --target staging --release <verified-release-id>` (specification only; script does not exist yet). If preconditions fail, stop that deployment design and choose a safe supported release mechanism; do not call an in-place upload atomic.

LiteSpeed's WordPress cache exclusions accept URI prefixes, e.g. `^/practice/`; changing the plugin remains subject to R1 approval. [LSCWP exclusions](https://docs.litespeedtech.com/lscache/lscwp/cache/). The server also supports Lab-local cache controls and `X-LiteSpeed-Cache-Control: no-cache`/`no-store`; it provides URL-scoped purge headers. [LiteSpeed developer controls](https://docs.litespeedtech.com/lscache/devguide/controls/). Prefer Lab-local exclusion plus normal `Cache-Control: no-store` for APIs, session pages and fixtures. Test repeated cross-session requests through the actual CDN; plugin configuration alone does not prove exclusion for a standalone PHP app. Keep immutable hashed assets cacheable; invalidate only Lab HTML/URLs if needed. Never purge the entire production site as an incidental deployment step.

## Research conclusion

Static Astro HTML with narrowly scoped interactivity is a strong fit for the served-HTML and WordPress-preservation rules. A separate PHP API under the Lab path can fit the available hosting model only after the actual runtime, storage and routing checks pass. Managed Node remains a legitimate alternative where the account and subpath routing support it, not an assumed capability or an automatically superior choice. Polling is the lowest-risk MVP real-time substitute on Web/Cloud PHP. SQLite, true atomic symlink releases and process isolation must not be reported as confirmed merely from vendor documentation.
